# Inspiration: semantic search inside Neon

## Goal

Semantic candidates never ran because they needed an Upstash index nothing filled. After: the embedding is a column on the row it describes, generated in Postgres by the database that already stores the wall. Proof: `pnpm inspiration import` leaves every active resource with an embedding, a query for "durable execution retries" returns resources whose text never contains those words, and `provider` reads `hybrid` with no API key anywhere.

## The change

```
was   wall row -> external index -> keep in sync -> semantic hits
now   wall row -> embedding column on that row  -> semantic hits
```

The middle step is the one that failed. It is now gone rather than automated.

## Why not the thing I built yesterday

`indexDocuments` shipped with zero callers, and that is the shape of the problem, not an oversight to patch. An index that lives in another service has to be pushed to, budgeted for, diffed against, and checked for emptiness. Every one of those is a way to be silently wrong. A column cannot drift from its own row.

Checked against your production database, all available and none installed:

| Extension | Version | Gives |
| --- | --- | --- |
| `vector` | 0.8.6 | pgvector storage and HNSW |
| `rag_bge_small_en_v15` | 0.0.0 | `embedding_for_passage(text)` and `embedding_for_query(text)`, both `vector(384)`, computed on the Neon compute |
| `rag_jina_reranker_v1_tiny_en` | 0.0.0 | local reranking, which `provider.ts` disables today because Upstash bills for it |

## The local database problem

`getInspirationDatabase` returns PGlite off Vercel. PGlite has no `rag_*` extensions and will never load a bundled embedding model, so the vector schema is **Neon only**:

```diff
-export async function migrate(db: InspirationDatabase) {
-  for (const statement of schema) await db.query(statement);
+export async function migrate(db: InspirationDatabase) {
+  for (const statement of schema) await db.query(statement);
+  // Embeddings are generated by a Neon server extension. Local PGlite keeps the
+  // full-text and trigram paths it has today and simply has no semantic column.
+  if (db.kind === "neon")
+    for (const statement of vectorSchema) await db.query(statement);
 }
```

Local dev behaviour is therefore unchanged from today: FTS plus trigram plus the BM25 wall. The semantic query returns nothing locally and the code already treats that as a normal outcome.

## The choices

### 1. The embedding is refreshed by the thing that writes the text

Not a command you remember to run. `indexDocuments` proved what happens to those.

```sql
UPDATE inspiration_resources
SET embedding = rag_bge_small_en_v15.embedding_for_passage(search_text),
    embedded_text = search_text
WHERE active AND embedded_text IS DISTINCT FROM search_text
```

Idempotent, incremental, and one statement. `importCatalog` runs it after its batches, so `pnpm inspiration import` is the only command in the loop and it already exists. First run embeds 1,363 rows; later runs touch only what changed.

`embedded_text` is what makes the guard exact. Comparing against `updated_at` would resend the wall on every import, since `importCatalog` bumps that whether or not the document changed.

Rejected: a `GENERATED ALWAYS AS (...) STORED` column, matching how `search_vector` is already derived from `search_text`. That would make drift structurally impossible, but generated columns require an IMMUTABLE function and one that loads a model almost certainly is not. Worth re-testing once the extension is installed; if it is immutable, `embedded_text` and the UPDATE both disappear.

### 2. Retrieval is a join, not a fetch

```diff
-      if (viewer.owner && text && (deps.hybrid || hasSearchProvider())) {
-        try {
-          const batches = await (deps.hybrid ?? hybridCandidates)(db, text);
+      if (viewer.owner && text) {
+        try {
+          const near = await db.query<{ id: string }>(
+            `SELECT id FROM inspiration_resources
+             WHERE active AND embedding IS NOT NULL
+             ORDER BY embedding <=> rag_bge_small_en_v15.embedding_for_query($1)
+             LIMIT 40`, [text]);
```

Candidates enter `addRanks` exactly as before, so RRF, the BM25 floor and the rest of the ranking are untouched. The `catch` that today reports a provider failure becomes the branch that fires when the extension is absent, which is the normal local case.

Semantic stays owner-only. It is no longer an API cost, but embedding the query is still compute on every search, and gating it keeps that bounded.

### 3. provider.ts goes

Deleting it removes `hasSearchProvider`, `hybridCandidates`, `indexDocuments`, the 1,800ms deadline, the `ingest:<month>` and `search:<month>` budgets, and two environment variables that were never set. `reserveUsage` stays; the login rate limiter uses it.

## Not doing

- No reranking yet. `rag_jina_reranker_v1_tiny_en` is available and the ranking already works without it; that is a separate change with its own before and after.
- No passage embeddings beyond the schema and the same refresh. There are 0 passages until `pnpm inspiration ingest` runs.
- No change to the search bar, to RRF, to the BM25 floor, or to who sees evidence.
- Not opening semantic search to anonymous visitors.
- Not installing the extensions on production as part of this. That is the first step of running it, and it is yours to approve.
